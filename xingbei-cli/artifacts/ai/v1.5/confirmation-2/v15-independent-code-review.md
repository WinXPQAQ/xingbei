## 高：盾被当作确定不响应，未知应战被提升为确定十万终局

位置：xingbei-cli/src/ai/v1.5-candidate/planner.js:23、:51、:119–134；model.js:157–158。

probability在有盾时直接返回shield分支，不计算合法圣光/应战。attackBranches又据此不设置uncertain。真实引擎先询问响应，只有没有响应才进入盾的命中检查。这不仅遗漏应战风险，还能让后续强制命中继承错误的确定性。

复现：运行 `node /tmp/v15-review.mjs`。风剑当前已完成1次攻击，持2张火系攻击和1水晶；蓝方1号持5张攻击（含火系）、有盾、蓝士气1。模型以count=1、depth=2规划第2刀+剑影第3刀，得到唯一概率1的shield→hit，蓝士气0，terminal=100000，总分100363.2。真实引擎第2刀允许1号用火系应战转向3号，1号手牌5→4且盾仍在；第3刀强制命中后4→6，蓝士气1，winner=null。对手手牌仅用于验证合法反例，未输入模型私牌。

修复方向：有盾也先分响应/不响应；仅不响应分支消耗盾。所有依赖未知响应的后续分支必须保留uncertain。增加真实引擎反例及无响应、强制命中对照，不能只给shield结果统一添加固定奖励。该项直接违背本轮用户确定/推测终局要求，发布阻断。

## 中：精确资源分配器的需求集合仍含永久无法兑现的宝石需求

位置：xingbei-cli/src/ai/v1.5-candidate/model.js:94–95；test/ai-v15.test.js:73–78。

allocationValue只扣除能够支付技能的现有能量，没有排除不能消耗的能量占满容量。例如狂战已有3水晶，无法消耗任意水晶，也无法提炼宝石，却仍对公共宝石提供需求溢价。脚本同一命令第二项输出：allocationValue=1.5200000000000014，energy={gem:0,crystal:3}，不可提炼。该场景可通过旧AI/人类合法提炼产生，并非非法输入。用于封闭需求集合的数学分配器确实精确，但可兑现需求建模不精确。

新DP测试把所有个人能量置0，并直接复用energyUses，因此只验证分配数学，不验证容量或技能可用性。建议加入满无用水晶、部分占位和可正常消耗柔性能量的正反例。此项中优先级，影响用户显式要求的容量/无法兑现例外，建议修复后重新冻结。
