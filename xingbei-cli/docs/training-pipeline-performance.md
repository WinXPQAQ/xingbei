# CPU/GPU训练管线优化（2026-11-12）

目标是提高贤者、魔弓的有效采样与训练吞吐，保持规则、观测、候选顺序、奖励、网络及训练配方不变。不同任务的模型和优化器独立；不替换线上AI。固定任务配比的三批采样对照，实际吞吐提高约22%；这不是胜率提升结论。

## 基线与记录

实验目录：`/home/xp/.local/share/xingbei-ml/pipeline-balance-20261112/`。

- `baseline.json` 保存源码哈希与固定模型来源：魔弓第170轮、贤者第193轮。
- `baseline/source/xingbei-cli/` 为改动前源码；实验快照另外保存，不修改原训练快照。
- `magic-observations.pt`、`sage-observations.pt` 是固定观测，供解码/打包微基准使用。
- `paired-benchmarks/` 是两任务同时采样的对照，每次96局魔弓、256次贤者练习；固定模型、种子、任务比例，六种配置各两次，第二次倒序运行。
- `warm-benchmarks/` 比较同一进程连续三轮采样时的进程复用；`full-benchmarks/` 再以实际批量验证选中的配置。
- `training-window*.json`、`*window.log` 记录基准窗口。脚本请求训练完成当前批次后让出机器，并在退出时恢复正常暂停的服务；规则失败状态不会被自动重启。

统计需区分：宿主总墙钟、每任务墙钟、进程CPU秒、GPU整卡采样、各阶段耗时。跨模拟进程的等待时间是累加值，不能当成墙钟耗时；CPU并行阶段与GPU阶段也不能直接相加。基准以采样为主，GPU平均利用率不能代替包含优化器更新的真实训练利用率。

## 已得到的证据

第一组两次平均总墙钟如下（含两个独立控制器初始化）：

|配置|魔弓/贤者模拟进程|总耗时|整机CPU忙碌率|采样期间GPU平均利用率|
|---|---:|---:|---:|---:|
|原版|64/32|36.39秒|65.6%|1.9%|
|仅减少进程|32/16|36.41秒|63.9%|3.8%|
|GPU打包、紧凑解码等|64/32|36.69秒|65.1%|3.1%|
|同上|32/16|36.49秒|63.6%|4.7%|
|同上|16/8|33.85秒|54.9%|11.2%|
|CPU打包、紧凑解码等|32/16|36.31秒|63.3%|4.3%|

不能只根据16/8配置的总时间就采用它：贤者单批变慢，需要继续平衡两个任务。提高GPU利用率并不自动提高总吞吐，64/32和32/16的GPU打包组合就没有明显整体收益。

魔弓基线首批中，模拟器CPU合计约684秒，规则教师决策计时约581 CPU秒。它们是多进程累计时间，实际采样约34秒。这表明规则陪练评分是该批主要CPU消费者，不能把CPU负担全归于规则结算或张量打包。另一次单局V8采样定位到`spellExposure`、`components`、`nextTurnRisk`及公共观测复制等热点。

## 实现与实验范围

- `binary_wire.py`：可选整帧索引转换，保留原有范围、长度、有限数值检查。把校验换成Python数值遍历更慢，已撤回该方案，数据保存在`decoding-view-validation-benchmark.json`。
- `batching.py`：可选GPU批量修正索引与掩码，用两次集中传输代替多次小传输。固定观测下张量内容一致；GPU数值比较使用绝对/相对误差1e-4，并记录旧实现重复执行自身的浮点波动。极近的候选同分不保证逐次argmax一致。
- 固定内存缓冲复用也做了微基准，收益不稳定且增加生命周期复杂度，暂不保留到运行实现。实验源码与结果在`pinned-experiment/`、`collation-pinned-benchmark.json`。
- `wire.mjs`：可选复用同一决策内的静态前缀特征计算；返回数组仍独立。题目、候选和后续伤害队列不进入静态前缀缓存。
- `binary-wire.mjs`：可选TypedArray批量写入；16位/32位传输帧与原版逐字节一致，大端机器仍走旧写法。
- `pool.py`：新增跨轮`GameRuntime`，只保留模拟进程，不保留游戏状态。每局重新创建游戏和编码器，失败/取消批次销毁借出的进程；上下文退出清理全部空闲进程。原`run_games`临时进程路径保留作对照。
- `worker.mjs`和`pool.py`增加分阶段计时：观测、打包、传输、教师、等待、解码、合批、推理；区分CPU时间与墙钟。
- 规则评分中，原本一次评价分别查询双方的法术风险，重复生成相同缓存键；改为一次取得双方结果，公式和分数不变。6局、2544次教师选择的完整选择哈希与旧源码一致；该对照只支持计算等价，不代表新强度评测。
- 共享资源配置由`XINGBEI_RESOURCE_BUDGET`和`XINGBEI_RESOURCE_JOB`选择，检查各任务声明的模拟进程数之和不超过总预算。预算指模拟进程，不是操作系统线程总数；具体部署分配须由实测决定。

## 最终选择与实际批量对照

采用总计32个模拟进程：魔弓16、贤者16，每个Python控制器1个Torch计算线程。魔弓使用GPU合批，贤者保留CPU合批；两者启用紧凑解码、批量写帧、前缀缓存及跨轮进程复用。模型仍按权重分别推理，优化器完全独立。配置在实验目录`resource-budget.json`；这是两服务共同遵守的进程预算，不是全系统强制资源隔离。

`full-benchmarks/` 每组连续三批，每批192局魔弓、512次贤者练习。固定检查点、种子、任务比例；原配置与新配置各跑一次完整组三批，较小批量对照另外做了重复。以下为采样测量，包含两个控制器初始化，不包含参数更新：

|指标|原配置64/32|新配置16/16|
|---|---:|---:|
|三批总墙钟|142.87秒|117.11秒|
|学习方有效决策/秒|384.79|469.24|
|累计CPU秒|3926.88|2047.70|
|整机CPU忙碌率|86.2%|54.9%|
|GPU平均利用率|3.1%|16.2%|
|整卡峰值显存|1217 MiB|1057 MiB|
|魔弓三批采样秒数|51.22 / 44.90 / 45.49|48.43 / 34.00 / 33.58|
|贤者三批采样秒数|12.75 / 11.16 / 12.74|4.97 / 5.79 / 6.29|

总吞吐约提高22%，耗时减少18%，累计CPU消耗减少48%。两个任务均加速。采样的GPU利用率不代表包含更新和评测的持续训练；不能把两份任务墙钟相加算总耗时。新旧GPU浮点求和顺序会产生极小差异，近乎同分的候选可能换序，因此实际学习方决策数为54976和54952，不宣称神经策略逐步完全相同。规则教师6局2544次选择一致，输入张量及候选顺序一致。

## 暂停、恢复与回退

安全暂停：分别在上述两个新目录创建`PAUSE`文件；等两服务自然结束当前批次，检查`status.json`为`paused`后再进行操作。不要用强行停止代替正常边界暂停。

恢复当前配置：删除新目录的`PAUSE`文件，然后执行：

```bash
systemctl --user start xingbei-magic-archer.service xingbei-sage-sustain.service
```

回退到优化前：先按上述方法暂停新服务。将各新目录的`previous-service.conf`分别复制到`~/.config/systemd/user/xingbei-magic-archer.service`和`~/.config/systemd/user/xingbei-sage-sustain.service`；删除旧目录`magic-archer-activation-20261112/PAUSE`和`sage-sustain-20261112/PAUSE`；执行`systemctl --user daemon-reload`后启动这两个服务。旧目录均位于`/home/xp/.local/share/xingbei-ml/`。这会从旧目录最后检查点继续，优化后训练成果保留但不自动带回旧运行。若恢复优化版，使用新目录中`continuous-service.conf`，同样重载服务并删除对应新目录的暂停标志。

规则教师评分仍是魔弓主要CPU热点。后续可以进一步缩减同局重复观测/风险查询，但需要另外验证评分等价。当前不增加网络规模、不改陪练配比，也不把整个规则引擎搬上GPU。
