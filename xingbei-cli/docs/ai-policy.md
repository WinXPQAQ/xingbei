# 确定性 AI（v0.6.0 历史基线）

当前生产入口已使用 AI v1.1（应用版本仍为0.6.3）：只增加攻击属性/目标的概率排序与软历史，防御、技能、弃牌沿用本页基线。当前结构、版本选择和限制见[版本说明](ai-versions.md)，实测结果见[实验记录](ai-v1.1-experiments.md)。下文记录原始v1.0策略及其历史验证，不代表本轮结果。

## 决策结构

`src/ai.js` 保留公开入口，具体策略分为四个模块：

- `ai/evaluation.js`：角色牌值、留牌组合、分牌收益、公开状态下的士气损失估算。
- `ai/actions.js`：枚举引擎允许的出牌、目标、技能费用/模式/目标组合和特殊行动，按收益减成本排序。`rankAiActions(game, playerId)` 返回行动、分数和原因，方便调试和后续调整。
- `ai/wind-plan.js`：搜索本回合直到第三次攻击的手牌顺序和额外行动来源，遵守风系限定行动优先、风怒/剑影每回合一次以及能量费用。优先少花能量；不修改 Game，不模拟未知摸牌。
- `ai/decisions.js`：响应、技能是否发动、费用牌、分牌、基础效果、治疗、虚弱/束缚的统一决策。

全部规则合法性和实际结算仍由 Game 验证。浏览器、终端、同步 AI 入口共用策略。爆牌新增显式 `overflow: "ai"`；原来的 `first`/`random`/`defer` 和明确索引仍可供规则夹具或调用方使用。

AI 只查看自己的牌、公开角色/状态/手牌数量；不读取对手、队友手牌内容或牌库顺序。确定性指同一状态的决策相同，不使用随机数打破平局；牌库洗牌依旧是游戏本身的随机机制。神官给队友的牌按角色适配度估算，不偷看队友是否已经持有同牌。

## 本批策略

| 项目 | 实现 |
| --- | --- |
| 提炼 | 通常只把恰好2颗的方案加入候选；战绩不足2或个人容量只剩1时拒绝。狂战优先宝石，其他角色优先水晶。例外需实际用途：神官敌方士气≤2、拥有领域费用与治疗且公开状态估算足以斩杀；风剑有至少3攻击，增加1能量后才能规划三刀。提炼占本回合特殊行动，斩杀/连击是后续回合机会估算。 |
| 狂战 | 撕裂在时点2根据当时伤害和目标治疗/手牌估算，只有新增士气损失才花宝石。 |
| 风剑 | 可完成三刀时优先整个顺序；非风疾风技靠前，风刀靠后，风系疾风技优先第二刀。不能三刀时拒绝额外消耗疾风技/剑影，免费风怒仍可使用。不假定未启用的英雄技能存在。 |
| 神箭 | 有法术、雷攻击或精准射击时更偏好高手牌对手；贯穿射击只在估计能压士气时弃法术，费用保留高价值牌。狙击考虑手牌上限4造成的直接爆牌及后续攻击。 |
| 封印 | 有后续攻击时法术行动加分，包括封印独有技；法术激荡后进入合法额外攻击。 |
| 天使 | 天使之墙仅选择自己/队友，要牌仅队友；要牌低分并扣除自身爆牌风险。洁净/天使之歌优先移除友方有害效果或敌方圣盾，羁绊治疗给己方有余量者。专属效果不能成为基础效果移除目标。 |
| 神官 | 水之神力联合枚举弃置的水牌、接收队友和可赠牌收益，排除已满手的队友。神圣领域考虑斩杀；启动时为已计划的行动预留能量和治疗，契约不会把必要治疗转走。 |

主动行动按评分竞争，并非每个偏好都是无条件立即执行。例如只剩一张中毒时，补牌可能比立即使用中毒更好；如果使用中毒，其目标仍按公开手牌数量评估。

## 牌值与留牌

牌值采用边际评分：每保留一张，就重新评估其他牌，以体现重复属性、重复圣光和法术数量。当前为有约束的贪心选牌，不宣称已经搜索所有最优手牌组合。

- 暗灭160起，第一张圣光140；后续圣光按重复数降值，通常低于本角色独有技牌。
- 通用普通攻击：未重复属性72，重复25；普通法术虚弱62、圣盾56、魔弹54、中毒52，重复继续减分。
- 狂战/风剑的普通法术降到约15，圣光仍单独保留；风剑疾风技高于风、风高于普通烈风技。
- 神箭/封印提高法术价值；非圣光法术达到手牌上限的一半后大幅降分，在牌源允许时至少留2攻击。保护暗灭和至少1圣光。封印独有技攻击可用于法术行动，因此价值更高。神箭闪光陷阱高于法术，精准射击与法术较接近。
- 天使首张风/水高于普通攻击，重复风/水收益下降；神官水牌接近其他角色的独有技牌，队友可接收的独有技牌高于自己的重复普通攻击。
- 神官在下次自己回合前有敌方狂战/风剑行动时，提高防御属性多样性：前2张普通法术优先，之后不重复攻击优先于更多法术，重复普通攻击最后。圣光和暗灭仍独立优先保留。

技能弃牌、爆牌、圣剑换牌共用牌值；赠牌使用接收者的角色牌值并扣除给予者的损失。治疗按避免爆牌所需数量使用，不会在空手且不影响士气时自动耗尽治疗。攻击和魔弹仍保留相同的人类选择/确认流程。

## 验证与复现

```bash
npm --prefix xingbei-cli test
node xingbei-cli/tools/benchmark-ai.mjs 100 xingbei-cli/artifacts/ai/benchmark.json a0588bd
```

基准工具从指定 Git 提交读取旧 `ai.js`，和当前 AI 在当前同一规则引擎下比赛。100个种子各交换红/蓝阵营，共200局；旧策略的虚弱统一选择跳过。旧神官若启动后失去行动费用，允许重新选择（本批2次），不把该错误直接判负。旧策略仍按旧实现随机爆牌/响应，新策略用牌值；这是整个策略的比较，不能用于单独归因某个评分项。

本批结果：69项 Node 测试通过；200局对旧策略178胜（红91/100、蓝87/100），无超时对局，最长116回合；单次行动评分观测最大约3.3ms（含旧策略，非性能保证）。另外种子101至200的100局新 AI 自博弈全部结束，最长92回合，每次行动检查牌实例位置守恒。

浏览器证据保存在 `artifacts/ai/`。整体两视口86项、狂战19项、神官29项、响应专项155项，共289项检查通过，控制台/资源错误0。开发魔弹场景首步与攻击场景一样使用明确脚本发牌，避免测试依赖 AI 自愿发起某种行动。首轮整体/响应脚本因 AI 选择补牌而未进入预期响应，狂战脚本原先假定 AI 总是耗尽治疗；已调整为明确场景动作及新治疗策略断言，不改变正式规则。

目前没有多回合对抗树、未知牌概率模型、对其他 AI 或真人的强度评估。风剑搜索只覆盖当前已知手牌及额外行动；期间被响应/封印等改变状态后重新规划，不能保证原计划必然完成。分数是可解释的初始策略参数，后续可用固定种子比赛、对战记录或学习方法改进。
